# Create a FlyonUI Vue component skeleton

Create only the skeleton of a new component and its documentation. Do not implement the actual component, its behavior, styling, examples, or substantive documentation.

1. Get the FlyonUI documentation section and component name from the request. If either is missing or ambiguous, ask for it. Check the navigation at https://flyonui.com/docs/getting-started/quick-start/ to identify the section and component; follow the component's link when needed to resolve its name. Do not guess when the source cannot be checked or the mapping is unclear.
2. Convert the component name to PascalCase and prefix it with `Fo` once (for example, Chat Bubble becomes `FoChatBubble`). Match the existing repository's section naming and directory conventions, even if the upstream section uses different capitalization. Check whether the component or destination files already exist; preserve existing work and do not overwrite it.
3. Inspect a comparable existing component and any applicable `AGENTS.md` instructions before editing. Follow current repository conventions instead of copying implementation details. Under `packages/core/src/UI/<Section>/<Component>/`, create the minimal matching structure, including `UI/Fo<Component>.vue`, `Types/<Component>.ts`, and the relevant `index.ts` barrels. The Vue template must contain the text `Implement Fo<Component>` as its placeholder, rather than an empty `<div>`. Create and export a `<Component>Props` type from the TypeScript file without inventing props; wire the Vue component to that type if appropriate. Export the component and its type through the existing public barrels, creating a section barrel and connecting it to the root only if the section is new and the project convention requires it.
4. Add documentation boilerplate in `packages/docs/<Section>/`, following a comparable component: a Markdown page and a `<Component>Docs.vue` wrapper in the component's docs folder. The wrapper must use `ComponentDocs`, with an explicit section prop whose type is the empty string literal (`type Section = ''`), an empty `Map<Section, FrameworkSectionPreview>` for previews, and `api-docs-component-names` set to the known `Fo<Component>` name. Bind the section and previews to `ComponentDocs` as in existing docs wrappers, and pass an empty section from the Markdown page. Add only the minimal placeholder content needed for a valid page; do not claim behavior or add working examples. Register the docs wrapper and sidebar entry where existing components are registered, if needed for the page to be reachable. For each new component entry in `useSidebarItems`, set `badge: _unreleasedBadge` using the existing badge. Never edit `packages/docs/Api/Lib/ComponentsApi.json`; it is generated.
5. Check that imports, exports, and documentation references resolve, and run the relevant available type checks or other proportionate validation. Report the files created and any checks that could not run. Keep the output as boilerplate even if the upstream documentation describes real functionality.
